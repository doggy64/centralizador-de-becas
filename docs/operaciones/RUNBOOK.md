# Operación del catálogo

## Preparación

Use Node y pnpm fijados en el repositorio. Tras la instalación congelada ejecute `pnpm build`. Instale Python 3.13 y `python -m pip install -r apps/worker/requirements.txt` en un entorno virtual. PYTHON_BIN permite seleccionar su ejecutable. El API solo necesita Node y acceso de lectura a PostgreSQL. El worker usa una cuenta editorial privada y sale a Internet únicamente para las tareas de descubrimiento o verificación autorizadas.

### Supabase

El proyecto Supabase `yunngepighxaigqkzpld` se conecta por su Session Pooler de us-east-1 en el puerto 5432. Copie `.env.supabase.example` a un archivo `.env` privado y reemplace únicamente `REEMPLAZAR_CON_PASSWORD_URL_ENCODED` por la contraseña de PostgreSQL codificada para URL. Aplique las migraciones y semillas con `pnpm build`, `pnpm --filter @becas/api db:migrate` y `pnpm --filter @becas/api db:seed`. La variable DATABASE_URL debe apuntar al pooler de sesión cuando se ejecute Prisma Migrate. Los servicios de contenedor reciben API_DATABASE_URL y WORKER_DATABASE_URL, ambas con la misma URI inicial.

Configure el secreto DATABASE_URL del propietario en el entorno del proceso de migración. Ejecute `pnpm --filter @becas/api db:migrate` y `pnpm --filter @becas/api db:seed`. Las semillas se pueden repetir. Cree logins separados para API y worker, aplique `infra/database/roles.sql` como propietario y otorgue respectivamente los grupos becas_reader y becas_editor. Mantenga el usuario propietario fuera de los procesos públicos. Para ejecutar la API use `pnpm start:api` con la URI de lectura. Para la CLI use DATABASE_URL editorial.

## Fuentes y revisión

1. Compruebe titularidad y edición en la página institucional. Registre una fuente con `pnpm editorial source URL manual --actor OPERADOR --note "Evidencia de titularidad"`. Para automatizar acceso revise condiciones de uso, ruta permitida y robots. Registre la decisión mediante `source URL crawl` con operador y motivo. El permiso se aplica al host exacto. Reserve la autorización de host para sitios cuyas condiciones permitan las rutas que se van a consultar.
2. Ejecute `pnpm editorial discover URL` para obtener enlaces en el host aprobado. El descubrimiento recorre hasta cinco páginas enlazadas con rel=next, una a la vez. Para una edición concreta, prepare un JSON con institution, program, editionKey y slug según los ejemplos de apps/worker/data. Ejecute `pnpm editorial ingest URL identidad.json --actor OPERADOR`. El worker conserva un fragmento o página, hash de contenido y resultado de ejecución. Un PDF sin texto queda NEEDS_REVIEW. Los 403, 429 y fallos de robots o red requieren reevaluar permisos y frecuencia antes de reintentar.
3. Para carga manual use `pnpm editorial import ruta.json --actor OPERADOR --dry-run` y después el mismo comando sin dry-run. Cada registro se valida dentro de una transacción. El rollback de la simulación incluye relaciones e historial. Para el lote institucional incluido use `pnpm editorial pilot --actor OPERADOR --dry-run` y después `pnpm editorial pilot --actor OPERADOR`. Son 15 candidatos de tres fuentes; la edición y la URL constan en cada JSON. Una interrupción permite repetir el lote.
4. Revise la ficha privada con `pnpm editorial inspect SLUG`. Compare con la fuente cada requisito, beneficio, importe, destino y plazo. Use fieldEvidence para cada condición o fecha confirmada. Para un día de cierre sin hora, guarde deadlineDay y originalDeadlineText. Registre timeZone únicamente si la fuente la confirma. La API aplica 30 días de frescura a comprobaciones activas y canales.
5. Envíe a revisión con `pnpm editorial submit SLUG --actor OPERADOR --note "Motivo"`. Compruebe los canales en la fuente. Un formulario externo debe estar designado explícitamente en el fragmento de evidencia y su sitio debe permitir la verificación. La CLI comprueba DNS, permisos, robots y redirecciones. Para correo, confirme el propósito y la dirección exacta en el texto oficial. Use `pnpm editorial channel ID VERIFIED --actor REVISOR --note "Cómo se verificó"`. Un canal PENDING permanece sin destino público accionable. Para invalidar uno cambie VERIFIED por INVALID o STALE.
6. El revisor humano usa `pnpm editorial publish SLUG --actor REVISOR --note "Campos y fuente corroborados"` o `reject` con el motivo concreto. Verifique el GET de detalle y la consulta por título. Para corrección use recheck o importe la edición corregida y vuelva a revisarla. Para retirar use retire. El historial queda asociado al identificador de la edición.

## Incidentes y seguimiento

Ante un destino sospechoso invalide el canal inmediatamente, retire la ficha si procede y registre el motivo. Para revocar una fuente use `source URL disable` con operador y motivo. La API excluye fichas respaldadas por fuentes revocadas. Compruebe 404 o urlOrEmail nulo antes de cerrar la incidencia. El revisor debe corroborar la fuente y la corrección para volver a publicar. Consulte IngestionRun por host, fecha y estado para investigar fallos; inspeccione ReviewEvent para reconstruir las decisiones. Una ejecución interrumpida puede quedar RUNNING, por lo que debe comprobarse el proceso antes de repetirla.

## Despliegue y recuperación

Conserve secretos y copias fuera de Git. En el despliegue con contenedores configure API_DATABASE_URL y WORKER_DATABASE_URL con los logins diferenciados y host interno db. Arranque primero PostgreSQL, aplique migraciones, roles y seed. Construya y arranque la API con `docker compose --env-file .env -f infra/compose.yaml -f infra/services.yaml up -d --build --wait api`. Ejecute el worker bajo demanda con los mismos archivos y `run --build --rm worker --health`. La API queda en loopback del host para el proxy HTTPS. Configure CORS_ORIGINS con los orígenes reales. Verifique /health, el catálogo y una ficha revisada después de cada despliegue. El flujo de GitHub Actions compila las imágenes y prueba ambos procesos.

Para respaldar use `pnpm db:backup ruta.dump` con pg_dump 17 y una cuenta autorizada. PG_BIN permite seleccionar el directorio de binarios. El comando exige un nombre de archivo nuevo. Para respaldo diario en Linux se incluyen becas-backup.service y becas-backup.timer en infra/database. Ajuste usuario y rutas al host, cree un directorio privado de respaldos y configure DATABASE_URL y BACKUP_DIR en /etc/becas/backup.env con acceso restringido. Instale las unidades y habilite el temporizador en el entorno autorizado. Transfiera las copias a almacenamiento protegido según la retención del operador.

Para ensayar la recuperación, cree una base vacía con sufijo _restore, configure RESTORE_DATABASE_URL y ejecute `pnpm db:restore ruta.dump`. pg_restore trabaja en una transacción. Compare conteos de Scholarship, Evidence, ReviewEvent e IngestionRun y consulte una ficha conocida. Aplique los permisos de roles antes del cambio de tráfico. Conserve la base original mientras se valida la recuperación. La ficha de demostración y las claves de las pruebas pertenecen exclusivamente al entorno local.
